I've completed a full line-by-line security, runtime, and architectural audit of **WCP Security Scanner v2.6.0** across all 168 PHP files (94,735 lines of code).

### Executive Verdict: Capability vs. Production Readiness

* **Architectural Capability (Strong Foundation)**: Your feature scope—spanning a multi-layered WAF (`FirewallEngine`, `MicroWafCompiler`, `VirtualPatchManager`, `AdaptiveRateLimiter`, `BotReconDefense`, `OutboundEgressFirewall`), AST/token-based malware and persistence hunting (`WebshellDetector`, `DeobfuscationEngine`, `HookInfiltrationSentinel`, `CronPersistenceScanner`), AES-256-GCM secret storage (`SecretVault`), hash-chained WAL activity logs (`WcpActivityLogger`), FIDO2/WebAuthn + TOTP 2FA, and transactional rollback—is comprehensive enough to compete with top-tier WordPress security suites.
* **Production Readiness (Not Ready — Stop-Ship Blockers Present)**: The plugin is **not yet safe for production deployment**. It currently contains **16 critical/high security vulnerabilities** (including 1-packet unauthenticated IP ban DoS, complete WAF/Virtual Patch bypasses, and unauthenticated log suppression), **22+ fatal PHP 8.3 runtime crashes / White Screens of Death (WSOD)**, **broken firewall rules** (`sanitize_text_field()` destroying payloads before regex evaluation), and **severe per-request database write bottlenecks**.

### 3. Deep Firewall Rules Review: Are All Firewall Rules OK?

**No — several firewall rules are currently broken or trivially bypassable.** Here is the exact status of your firewall rules in `FirewallEngine.php` and `VirtualPatchManager.php`, why they fail, and how to fix them:

#### A. Why Core WAF Rules Are Currently Broken (`FirewallEngine::evaluate_rules()`, `L1633–1850`)

1. **`sanitize_text_field()` Destroys Attack Payloads Before the WAF Can See Them (`L1633–1635` & `VirtualPatchManager.php:448`)**:
* At `L1633–1634`, you run:
```php
$uri = isset($_SERVER['REQUEST_URI']) ? sanitize_text_field(wp_unslash($_SERVER['REQUEST_URI'])) : '';
$query = isset($_SERVER['QUERY_STRING']) ? sanitize_text_field(wp_unslash($_SERVER['QUERY_STRING'])) : '';

```


* WordPress's `sanitize_text_field()` calls `wp_strip_all_tags()` (which strips `<script>`, `<iframe>`, and `<?php` tags) and **deletes all percent-encoded octets (`%[0-9a-fA-F]{2}`)**!
* Because `sanitize_text_field()` runs *before* `urldecode()`, a path traversal attack like `/index.php?file=..%2f..%2fwp-config.php` has `%2f` stripped and becomes `....wp-config.php` before `urldecode()` runs!
* As a result, your rules for `..%2f`, `..%5c`, and `%00` (`L1651`, `L1755`, `L1756`) are **100% dead code** on `$uri` and `$query`, and URL-encoded XSS/PHP-injection in the query string or path is silently stripped during WAF inspection while WordPress/PHP still receives the real raw `$_GET` / `$_SERVER['REQUEST_URI']`!
* **Fix**: Never call `sanitize_text_field()` on inputs being inspected by the WAF. Inspect raw `wp_unslash($_SERVER['REQUEST_URI'])` and iteratively decode (`rawurldecode()` + `html_entity_decode()`) up to 3 passes before running regex rules.


2. **Uninspected Request Vectors (`$_COOKIE`, `HTTP_USER_AGENT`, `HTTP_REFERER`, and Bodies > 128 KB)**:
* `$user_agent` is assigned at `L1636` in `evaluate_rules()`, **and then never used anywhere in the function**! SQLi/XSS/RCE payloads in `User-Agent`, `Referer`, or `$_COOKIE` pass straight through.
* At `L1720`, `if (strlen($raw_input) < 131072)` skips `php://input` inspection whenever the request body is `>= 128 KB`. Sending a 129 KB JSON or XML-RPC request bypasses 100% of raw-body WAF rules.
* **Fix**: Inspect `substr($raw_input, 0, 131072)` instead of skipping the entire body when `>= 128 KB`, include `$_COOKIE` keys/values in `$all_inputs`, and run SQLi/XSS/RCE patterns against `$user_agent` and `HTTP_REFERER`.

### 5. Severe Per-Request Performance Bottlenecks

Right now, the plugin executes heavy database reads and writes on **every single frontend and backend HTTP request**:

1. **3 `SHOW TABLES LIKE` Queries on Every Page Load (`includes/Plugin.php:28–30`)**:
* `Plugin::ensure_Critical_Schema()` runs `SHOW TABLES LIKE 'wp_wcpscan_scans'`, `SHOW TABLES LIKE 'wp_wcpscan_firewall_logs'`, and `SHOW TABLES LIKE 'wp_wcpscan_login_history'` on every request before checking `wcpscan_db_version`.
* **Fix**: Check `get_option('wcpscan_db_version') === WCPSCAN_DB_VERSION` **first** (which uses WordPress's in-memory `alloptions` cache in 0 queries), and only run `SHOW TABLES` when the version option is missing or outdated.


2. **2 `set_transient()` Database Writes on Every Request (`FirewallEngine.php:689–692` & `AdaptiveRateLimiter.php:188`)**:
* On sites without Redis/Memcached, `set_transient('wcpscan_active_visitor_traffic_15s', ...)` (`FirewallEngine.php:690`) and `set_transient('wcpscan_rl_global_...', ...)` (`AdaptiveRateLimiter.php:188`) execute `INSERT/UPDATE` queries against `wp_options` on **every visitor page view**, causing severe InnoDB row lock contention under high traffic.
* **Fix**: Only write the active visitor traffic transient if it is not already set (`if (!get_transient('wcpscan_active_visitor_traffic_15s')) set_transient(..., 1, 15)`), and use APCu / object cache or file-backed counters in `/dev/shm` or `.logs/` for per-second rate limiting when `wp_using_ext_object_cache()` is false.


3. **Autoloaded `update_option('wcpscan_learning_route_profiles')` on Every Clean Request (`LearningModeEngine.php:224`)**:
* `LearningModeEngine::observe_request()` runs on every clean request (`FirewallEngine.php:1600`) and calls `update_option(self::PROFILES_OPTION, $profiles)` on every request once a route hits 25 samples (`L213–224`), flushing WordPress's `alloptions` cache on every hit!
* **Fix**: Gate `LearningModeEngine::observe_request()` so it only runs when `$settings['waf_mode'] === 'learning'`, and do not call `update_option()` if `$profiles[$route_key]['graduated']` was already `true` and no new param keys were added.


4. **Double Disk Read + SHA-256 Hash on Every Request (`WcpJitMuGuardian.php:48–65`)**:
* `EphemeralAdminEngine::init()` calls `WcpJitMuGuardian::ensure_installed()`, which calls `file_get_contents()` and `hash('sha256', ...)` on both the MU-plugin file and source string on every HTTP request.
* **Fix**: Only run `ensure_installed()` when an ephemeral admin or support user is actually active (`!empty(get_option('wcpscan_ephemeral_admins')) || !empty(get_option('wcpscan_support_users'))`) or during admin requests.
